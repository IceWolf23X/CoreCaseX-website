Storage model

SQLite is authoritative. A dedicated single-thread executor serializes asynchronous storage work. Each operation opens a connection, enables foreign keys and closes it after use.

Tables cover cases, timeline, replies, internal notes, one resolution per case, evidence and schema migration markers. Indexes support reporter history, board status/priority, assignments and chronological detail queries.

Transaction boundaries

Creation writes the case, CREATED event and initial evidence in one transaction. Claim, assignment, priority, status, replies, notes, request-info, closure and archive likewise keep the state mutation and its timeline/reply/note/resolution record together. Startup waits for migrations before registering the working command surface.

Offline backup procedure

  1. Stop the Paper server.
  2. Copy the entire plugins/CoreCaseX/ folder to a protected location.
  3. Verify the backup contains all five YAML files and data/corecasex.db.
  4. Start the server and perform one read-only case check.

There is no online backup or restore command. Do not copy a live database and call it verified without testing that copy separately.

Changing the database path

Stop the server, back up the folder, move/copy the database to a safe relative path, update storage.yml, then restart. A reload alone does not move data or reopen SQLite.

Intentional removal

Deleting data/corecasex.db deletes every case, evidence record, reply, note, resolution and timeline entry. Regenerating YAML never requires deleting the database.
