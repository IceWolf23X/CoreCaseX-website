Five case types

  • Support request: description, optional current location and reporter snapshot.
  • Player report: online/offline target name, configured reason, description, reporter location and an online target snapshot when available.
  • Bug report: configured category, description and optional current location.
  • Lost items / death issue: description, claimed items and optional latest death context observed since plugin startup.
  • Grief / theft: description, optional current location, manual location text and HIGH priority by default.

Every type can be enabled or disabled and has a configurable default priority. The exact limits of collect-location are documented under case-types.yml.

Staff board and actions

Filters cover all open, unassigned, assigned-to-me, high/urgent, waiting-player, waiting-staff, recent-closed and archived cases. Permission-controlled actions include claim, assign/reassign, priority, status, internal note, player-visible reply, request info, teleport to an attached location, resolve, reject and archive.

Evidence and visibility

Evidence entries are PLAYER_VISIBLE, STAFF_ONLY or SENSITIVE. The latter two require separate staff permissions. Player-facing case access also verifies that the viewer is the original reporter.

Notifications

In-game notifications cover new cases, reporter replies and assignment. Optional Discord webhooks can mirror eleven event families and route by priority, then case type, then default/legacy fallback.

Persistent history

SQLite stores cases, evidence, replies, notes, resolutions and timeline events. State-changing storage operations use transactions so the case mutation and its history remain together.
